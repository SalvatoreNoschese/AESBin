# Security model

```
Master password ── Argon2id ──┐
Recovery phrase ── Argon2id ──┼─► KEK (Key Encryption Key, never stored)
Passkey ─────────── PRF ──────┘     │
                                    └─ unwraps MASTER_KEY (its own wrapped copy per KEK, in the DB)
                                          │
                                          ├─ wraps per-file DEK ──► AES-256-GCM ──► ciphertext on disk (.bin)
                                          │
                                          └─ encrypts metadata (filename, MIME type, description, checksums)

Share link:  https://host/s/{16-char token}#{32-hex KEY}
                                            └── URL fragment (KEY): never in the request line or Referer; sent once to the
                                                server on open, where shareKey = BLAKE2b(key=KEY, salt) unwraps the DEK
```

The server stores only ciphertext, wrapped (encrypted) DEKs and encrypted metadata. Without the master password, the recovery phrase or a passkey (with its PRF output), no file content or filename can be recovered, not even by someone holding a full copy of the server's database and disk.

## Design notes

**Two different key derivations.** Argon2id is memory-hard and slow on purpose. It protects the master password and the recovery phrase because a person picked them, and slowing down guesses against human input is its whole job. The share `KEY` in the diagram is different: a 128-bit random value generated by AESBin, never chosen or memorised by anyone, with nothing to guess. Stretching it would add latency and no security. Share subkeys (one per file, plus the target's name and description) are therefore derived from it with a fast keyed BLAKE2b hash, the role HKDF plays in many protocols. In practice this matters when sharing or retargeting a directory with many files: at Argon2id cost that could stall on modest hosting, at BLAKE2b cost it is instant.

**HTTPS is mandatory, enforced at boot.** Passwords, recovery phrases and the wrapped MASTER_KEY all cross the wire in normal use, and browsers silently reject the `__Host-` session cookie over plain HTTP anyway (sessions would never persist, with no clear reason why). Rather than run half-broken, AESBin refuses to start without HTTPS.

HTTPS is detected natively or from a reverse proxy's `X-Forwarded-Proto`, `X-Forwarded-SSL` or `CloudFront-Forwarded-Proto` header. Clients can send those headers too, so they count **only** when the request comes from an address in `security.trusted_proxies`, the same rule `request_ip()` applies to `X-Forwarded-For`. If you terminate TLS at a proxy, list its addresses there. `'force_https' => true` in `config.php` is a manual override for when detection fails, not a way to run without HTTPS.

**HSTS is yours to set, not the app's.** `Strict-Transport-Security` applies
to the whole host, not only to AESBin: sent from here, it would decide for
every other page on the same domain, and two copies of the header (one from
the app, one from the server) leave the browser to obey whichever comes first.
So AESBin does not send it, and the choice stays with whoever runs the
server. If the site is HTTPS-only, turn it on there, once, for the domain:

```apache
# Apache (.htaccess or vhost), only on HTTPS responses
Header always set Strict-Transport-Security "max-age=31536000" "expr=%{HTTPS} == 'on'"
```

```nginx
# nginx, in the server block that listens on 443
add_header Strict-Transport-Security "max-age=31536000" always;
```

On cPanel it is a switch under **Domains** (HSTS), per domain. Add
`includeSubDomains` only if every subdomain is HTTPS too, and `preload` only
after reading [hstspreload.org](https://hstspreload.org/): leaving the preload
list takes months. Whatever you choose, a browser that has seen the header
refuses plain HTTP, and any certificate warning, for `max-age` seconds.

**Session behaviour.** After login you are not asked for the password on every operation: the PHP session keeps the MASTER_KEY wrapped with a per-tab key that the browser sends with each request, and the server unwraps it for that request only. The session cookie on its own therefore reaches very little: every authenticated endpoint except logout, the session-status probe and dropping an elevation window early (all three only ever reduce what the session can do) requires that key, either because it decrypts or because it proves it holds the key before acting (`Auth::requireKeyHolder()`), so a leaked cookie cannot revoke shares, end other sessions or open an elevation window. Someone with full server access *while you are logged in* could therefore capture it in transit or from process memory (see [Threat model](#threat-model)). Logging out destroys it. This is not how a password manager like Bitwarden or a storage service like MEGA works: those decrypt only on the client and never hold your key on the server, even briefly. AESBin's trade-off is the one most self-hosted encrypted file tools make to stay easy to deploy on shared hosting. If you need a stricter model, make sure the server is trusted and keep sessions short with `session_idle_timeout`.

**Passkey login (PRF extension).** A normal WebAuthn passkey only proves *who you are*, with a signature; it hands the application no secret. **PRF** is an optional extension that also lets the authenticator *derive* a deterministic secret from a salt, without the private key or anything derived from it leaving the device. AESBin uses that output where the password flow uses the Argon2id KEK: to wrap and unwrap the MASTER_KEY. The server never sees or stores the PRF output, only the wrapped result, which is bound to the passkey it was made for: the credential's id is its associated data, so a copy moved under another passkey does not open. The MASTER_KEY itself does cross the wire at passkey login and registration; see [⚠️ Passkeys](#threat-model) in the threat model.

That is why passkey login **requires** PRF: without it, the authenticator can prove your identity but cannot provide key material to decrypt anything.

Support depends on the authenticator and browser, and changes quickly. Roughly, as of mid-2026:

- **Android + Google Password Manager** (Chrome, Edge, Samsung Internet): supported by default.
- **Apple iCloud Keychain** (Safari 18+, macOS 15+, iOS 18+): supported for the built-in authenticator only. An external security key on an iPhone or iPad cannot pass PRF through; that is an iOS limit, not the key's.
- **Windows Hello**: newer and version-dependent. Treat it as "sometimes" until you have tried it on your setup.
- **Hardware keys** (YubiKey 5 and similar): generally supported on desktop Chrome; blocked on iOS as above.
- **Password managers** with passkeys: coverage varies and changes between releases. One that saves the passkey but returns no PRF output cannot unlock the vault; AESBin detects this at registration and says so.

If your combination lacks PRF, AESBin says so at registration instead of failing silently, and password + TOTP keeps working as before. A provider that saved the passkey anyway is asked to drop it (`signalUnknownCredential`, where the browser supports it); otherwise delete it from the AESBin entry by hand. Treat the list above as a snapshot: if you believe PRF should be available and AESBin says it is not, check your browser and OS versions first.

## Threat model

This section says what AESBin protects against and where the limits are. Being explicit about both is more useful than claiming "zero knowledge" without qualification.

**✅ Database stolen (server at rest)**

A full database dump contains encrypted file metadata, wrapped DEKs and wrapped copies of the MASTER_KEY; the file contents are ciphertext on disk. Without the master password, the recovery phrase or a passkey with its PRF output, none of it can be decrypted. Brute-forcing the password is made expensive by Argon2id (64 MiB, 3 iterations per guess). This is the scenario AESBin is primarily designed to defeat.

**ℹ️ What stays visible without the password (metadata)**

Some fields cannot be encrypted without breaking the app. File **size** is stored in plain text (for quotas and upload progress), and so are timestamps (created, modified, trashed), download and visit counts, and how many files and folders you have. So is the operational record: the activity log (your own IP addresses and browser labels, the referrers of share visits), the active-sessions list and, for at most two hours, the rate-limit table's client addresses. Anyone with database access learns *how much* you store, roughly *when*, and from where you logged in; never *what it is* or *what it's called*: names, descriptions, MIME types and content stay encrypted.

**✅ Share links intercepted**

Browsers never put the URL fragment (`#key`) in the request line, so the key does not appear in server access logs or in Referer headers. It does stay in the address bar, the visitor's browser history and any bookmark or synced tab, exactly like the link itself: anyone with access to that browser has the link. Someone who only has the token part of the URL, without watching the link actually being opened, cannot decrypt the shared content. The key *is* sent to the server once: in the `/api/share/auth` POST body, when a visitor opens the share, because decryption happens on the server.

**✅ Session file stolen from disk**

The PHP session holds the MASTER_KEY encrypted with a per-tab key that lives only in that tab's `sessionStorage` and is never written to the server's disk. A dump of the server's session files yields ciphertext and nothing else. The key is not shared between tabs, not stored in a cookie and not broadcast anywhere; the cost is that each new tab needs its own login (see [SECURITY.md § Accepted risks](../SECURITY.md#accepted-risks)).

**⚠️ Server compromised during an active session**

An attacker with root access *while you are logged in* can capture the per-tab key from the next request (`X-Session-Key`), or read the MASTER_KEY from the PHP process while a request is using it, and decrypt anything you can. The session file alone is not enough (see above). This limit applies to any web application that decrypts on the server, Nextcloud included. Mitigations: short sessions (`session_idle_timeout`), logging out when done, and turning on `session_ip_lock` (off by default) where the connection keeps one address.

**⚠️ Upload: a brief plaintext temp file**

When you upload a file, PHP itself writes it to a temporary directory in plaintext before any application code runs; that is how every PHP application receives uploads. AESBin reads that file, encrypts it and writes only the ciphertext to storage. It never moves the plaintext copy, so PHP deletes it when the request ends, usually well under a second later for small files. Worth knowing if your host's temp directory has loose permissions or sits on storage you do not otherwise trust.

**⚠️ The MASTER_KEY never changes**

One MASTER_KEY is generated at install time and lives for the life of the
installation. A password change, a new passkey and a recovery-phrase rotation
all re-wrap that same key rather than replacing it, so anything encrypted
before a credential change stays readable with the key as it was.

The key alone is not enough to read anything: the per-file DEKs it unwraps
live in the database, so a MASTER_KEY plus the blobs on disk decrypts nothing.
Paired with a database dump, though, it reads every file in the instance, and
because the key never changes, that stays true for files uploaded afterwards
as well. Changing your password does not take that away.

A database dump plus the key also yields every live share link: the token is
stored in plain text and the link's key is stored encrypted with the
MASTER_KEY (that is how the dashboard can show you the full URL again). Those
links then work from anywhere, through the public share page, with no further
access to the server. And with *write* access to the database, the key is
enough to wrap it under a password of the attacker's choosing and, since the
TOTP secret is readable too, to log in as you.

There is no rotation command: the way out is a new installation and a
re-upload, with every share link revoked or left to die with the old instance.

**⚠️ Passkeys: the MASTER_KEY crosses the wire**

At passkey login the browser unwraps the MASTER_KEY with the PRF output and sends it to the server in one HTTPS request, authenticated by a valid WebAuthn assertion; from then on the session works exactly as after a password login. Registering a passkey does the reverse: the server hands the MASTER_KEY to the page so it can be wrapped with that authenticator's PRF output. In both cases the key is inside TLS and in page memory only briefly, but a script injected into the page at that moment could read it.

**✅ Recovery phrase**

The 10-word recovery phrase is stored with the same Argon2id parameters as the master password, and at 110 bits of entropy (10 words from the 2048-word BIP-39 list) it is out of reach of brute force.

It is also the most powerful credential in the system: it resets the password, the TOTP secret and itself. Rotation exists so that a single leak (a photographed copy, say) is not permanent. But rotating also invalidates the copy the owner keeps on paper, and whoever rotates first keeps the account. So rotation lives only in the recovery flow, which requires the *old* phrase (not by policy: without it the MASTER_KEY cannot be unwrapped, so there is nothing to re-wrap), behind both gates below. It is absent from the dashboard, where a stolen session would be enough to reach it.

Recovery is **off by default**, behind `'recovery' => 'yes'` in `config.php`. With the gate shut, every recovery endpoint answers 403 before looking at the phrase, `/recovery` redirects to the login page, and the link is absent from the login screen and the settings card. A stolen phrase is inert.

Opening the gate means editing `config.php` over FTP/SFTP/SSH: the same proof of server ownership the installer asks for, and the one thing a phrase thief does not have. It is not settable from the dashboard, because an intruder with a stolen session must not be able to open the door they are standing behind. The gate closes itself after a successful recovery, and while it is open the dashboard shows a banner. Both directions depend on PHP re-reading the file: on a server with OPcache set not to revalidate and no usable `opcache_invalidate()`, neither takes effect until PHP restarts, and Settings → Server requirements reports that.

**The guard file.** The flag alone is not enough. Once open, it lets anyone who reaches the URL through, and someone holding a stolen phrase could poll `/recovery` until the 403 turns into a 200 and race the owner. So the flag only says recovery is *permitted*; a second proof says *who is asking*. Visiting `/recovery` creates a `_recovery/` folder in the storage directory with a randomly named file inside, containing an 8-character code that is never sent in any response. Reading it takes FTP/SFTP/SSH or a hosting file manager, and the phrase field stays unreachable until it is entered.

It is the installer's `_viewme/` mechanism (`app/includes/GuardFile.php`) applied to a different problem, with its own directory and lifetime. Each has its own folder so that checking for a stale one costs a failed `is_dir()` rather than a directory read, which keeps the cleanup cheap enough to run on every request. It lives in storage rather than the app root because the root is read-only on hardened installs, and a guard file that could not be written would make recovery impossible on the most careful setups. Storage is always writable, since uploads land there.

It is never served. The `.htaccess` written into the storage directory at boot refuses everything there with a 403, by path, so a guessed name and the real one get the same answer. The file is also a PHP stub that refuses on its own, the last line of defence on a server that ignores `.htaccess` and has not been given the deny rule from [Installation](installation.md). Once those rules are in the server's own configuration, `'server_rules_configured' => true` in `config.php` tells the dashboard, since PHP cannot read an nginx or Caddy config. On a server that does not execute PHP in the storage directory (sensible hardening), the stub would be served as text, so there the deny rule is what protects the file.

There is **no time limit** on the code. Three barriers already stand in front of the phrase (an unlinked page, a config edit over FTP, a code read from disk), and a countdown would add little while risking the one failure this flow cannot afford: stranding the owner halfway. Wrong codes are throttled instead, in their own bucket (`recovery.guard_fail`), so a mistyped code never uses up the attempts left for the phrase.

The file is removed by one rule in `bootstrap.php`: if the gate is shut and a guard file exists, it is deleted, on any request at all. A check limited to the recovery endpoints would miss the case that matters most, since a completed recovery closes the gate inside its own request. The same rule clears `app/setup/_viewme/` once `config.php` exists, which also covers an FTP client that re-uploads the file when its editor closes.

**Rotation, in practice.** Password, TOTP secret and phrase are three independent choices in the recovery form, in any combination: wanting a new TOTP secret does not force a new password. A new phrase is shown *before* anything is written, and the confirm button stays locked until it has been copied or downloaded and acknowledged, as in the installer. A new TOTP secret is shown the same way, and saved only once a code from the authenticator has been verified for it, as in the installer: the owner leaves the page already able to log in. A phrase delivered only in the response that activates it would be lost if that response never arrived, and nothing recovers a lost phrase; an unverified TOTP secret could leave the owner with a password that no longer logs in, passkeys already removed and the gate closed again. Everything requested is then applied in a **single UPDATE**: a partial write (new password, old wrapping) would leave an installation nobody can open.

**What every recovery also does.** Two things are not among the choices, because a recovery is the moment to start again from credentials you know:

- **Every passkey is removed**, in the same UPDATE. A passkey unwraps the MASTER_KEY without password or TOTP, so it survives every rotation the form offers. Anyone who knew the password could elevate and register one, and nothing in the settings list tells it apart from yours for certain. Keeping it optional would also let an owner recover "just in case" and carry on with the old passkey, never learning whether the recovery achieved anything. Register your passkeys again after logging in.
- **Every session is ended.** A session opened with the old credentials would otherwise keep reading until its idle timeout, and one still inside its elevation window could register a passkey after the recovery. The browser running the recovery holds no authenticated session, so you only log in again, as you would anyway.

The result is an asymmetry. An attacker with your password and TOTP can read, and can add a passkey, but cannot change the password, the TOTP secret or the phrase (there is no authenticated path to them) and cannot lock you out for good. They can keep TOTP logins blocked by failing codes on purpose, and remove your passkeys, but recovery always works: it clears that block, removes whatever they added and ends their session. An attacker with your phrase cannot use it without the server. You, owning the server, always have both routes.

**ℹ️ Contact email in the page source.** Obfuscated so scrapers do not get it in plain text; [SECURITY.md § Accepted risks](../SECURITY.md#accepted-risks) explains how, and the limits.

**Out of scope**

AESBin does not protect against malware on your own device (keylogger, compromised browser), physical access to an unlocked device, or a malicious server operator who changes the PHP code served to your browser. For those, a native app with local-only encryption (Cryptomator, VeraCrypt) is a better fit.

## Elevation

Some settings ask for the master password again inside an active session ("elevation") before saving: rate limiting, ALTCHA, session policy, revealing the TOTP secret, adding or removing passkeys, upload and storage limits, the activity-log item cap, the privacy/contact details shown on public pages, the one-click `.htaccess` 403 fix, and recording the storage path the installer offers on reconnect. Elevation also guards what cannot be undone: permanently deleting a file (one at a time or with "Empty trash"), purging the activity log, integrity repairs and database migrations. Ordinary file, folder and share actions do not ask: creating, editing, retargeting or revoking a share, and moving a file, directory or container to the trash, shared or not.

The line is drawn there because a logged-in session can already read, download and decrypt every file in the instance. A second password check on file or share actions adds friction without protecting anything the session cannot already reach. What elevation guards against is a session changing what the instance *is* from then on (a rate limit turned off, a passkey the owner did not add, the captcha disabled) because those outlive the session and lower the bar for whatever follows. Revoking a share or trashing a file only removes access the session already had; the worst case is recreating a link. Destroying data permanently is the other side of the line, so it asks.

What elevation defends against is narrow: a stolen session *cookie* together with the tab's session key, without code running in the page (a leaked log line, a misconfigured proxy, a browser extension that reads cookies but cannot inject scripts). It does nothing against XSS inside the page, which can draw its own password prompt and phish the real password. The real defences against session theft are elsewhere: `HttpOnly`, `SameSite=Strict` and `__Host-` cookies, mandatory HTTPS, CSRF tokens, TOTP on every login and `session_ip_lock`, once turned on (it is off by default) and with the proxy configured correctly (`security.trusted_proxies`, see [Configuration](installation.md#configuration)).
